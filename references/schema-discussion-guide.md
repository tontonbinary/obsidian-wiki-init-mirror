# Schema 讨论指南

> 用于 Agent 与用户讨论并确定 SCHEMA.md 的参考文档
> 每个 Agent 有自己的 SCHEMA.md（专用配置）

---

## 完整流程

### 讨论前

1. 告知用户讨论时长（15-45分钟）

### 讨论中

1. 先讨论 Q1-Q2（vault 定位、raw 分类）
2. **Q1-Q2 讨论完立即跑 `init_vault.py` 创建基础目录**
3. **Q1-Q2 讨论完立即跑 `activate.py` 注册 heartbeat**
4. 继续讨论 Q3-Q5（wiki 分类、命名规范、编译触发）
5. 讨论过程中可以调整目录结构

### 讨论后

1. 填充 SCHEMA.md（填入讨论结果）
2. 删除 🟡 待填充标记
3. 更新状态为 ✅ 已确认

**⚠️ 禁止只讨论不执行。每个阶段完成后必须运行对应脚本。**

---

## ⚠️ 讨论时长提示

**讨论耗时约 15-45 分钟，涉及 5 个问题。**

建议开始时告知用户：
> "这次讨论大概需要 15-45 分钟，涉及 5 个问题。"
> "如果中途有其他事要处理，可以随时暂停，我们会记录进度，下次继续。"

---

## 讨论原则

### 1. 逐项进行，不一口气问完

每次只讨论一个问题，确认后再问下一个。

**❌ 错误示范：**
> "咱们来建知识库，我一次问你5个问题：1.给谁用？2.raw要哪些分类？..."

**✅ 正确示范：**
> "咱们先确定第一个问题：这个 vault 给谁用？"

---

### 2. 边讨论边填，不等最后汇总

每项讨论确认后，**立即填到 SCHEMA.md**，不要等全部讨论完再填。

这样如果讨论中断，SCHEMA.md 已有部分内容，下次容易接上。

---

### 3. 用实例帮助理解

每个问题用具体例子说明，帮助用户做决定。

## Q1: 这个 vault 给谁用？（必须深入讨论）

### 这是什么意思？

确定 vault 的**边界**——什么信息属于这个 vault，什么不属于。

### 为什么重要？

- 不同 Agent 的知识边界不同
- 边界模糊会导致 wiki 内容混乱
- 影响后续 compile 和 lint 的判断标准

### 常见选项

| 选项 | 说明 | 例子 |
|------|------|------|
| Agent 专用 | 某个 Agent 的知识库 | Xiaoxian、Mautoer、TS |
| 项目专用 | 某个项目的知识库 | ChatERP、某产品 |

### 讨论示例

> "这个 vault 是给 TS（服装商品AI助手）用的，还是给某个项目用的？"

**讨论确认后，立即填到 SCHEMA.md：**
```markdown
## vault 定位

- 使用者：Mautoer
- 定位：Mautoer 开发总控知识库
- 知识边界：
  - ✅ 记录：OpenClaw 系统配置、踩坑记录、周期性可能发生的问题
  - ❌ 不记录：日常维护记录
```

---

## Q2: raw/ 需要哪些分类？（快速确认）

### 这是什么意思？

raw/ 是**原始材料仓库**，放还没整理的信息。

### 默认分类和含义

| 文件夹 | 存放什么 | 例子 |
|--------|---------|------|
| **文章/** | 公众号、博客、RSS 订阅 | 服装行业分析文章 |
| **文档/** | PDF、手册、飞书文档 | 库存管理手册 |
| **对话/** | 聊天记录、会议记录 | 与客户的对话摘要 |
| **环境认知/** | 工具配置、用户偏好、角色关系 | 团队成员昵称表 |
| **日记/** | 工作日志 | 今日工作总结 |

### 讨论示例

> "raw 默认分5类：文章放公众号/博客，文档放手册/PDF，对话放聊天记录，环境认知放工具配置/团队关系，日记放工作日志。你有要增减或改名的吗？"

**常见调整：**
- TS 可能需要 `订单/` 替代 `日记/`
- 技术型 Agent 可能需要 `代码/` 或 `日志/`

**讨论确认后，立即填到 SCHEMA.md：**
```markdown
## raw/ 分类

| 文件夹 | 存放内容 |
|--------|---------|
| 文章/ | 技术文章、行业分析 |
| 文档/ | PDF、手册、设计文档 |
| 对话/ | 与其他 agent 的对话 |
| 环境认知/ | 工具配置、团队关系 |
| 日记/ | 工作日志、踩坑记录 |
```

**可选添加（技术型 Agent 需要时）：**
- `代码/` — 代码片段、CLI 命令

**Q1-Q2 讨论完，立即运行：**
```bash
python3 $SKILL_DIR/scripts/init_vault.py <vault-name> <vault-path>
python3 $SKILL_DIR/scripts/activate.py <vault-path> [agent-name]
```

## 实例引导（Q2 后、Q3 前必须执行）

**目的：** 从 Agent 的 MEMORY.md 找出适合提取到 wiki 的内容，逐条和用户讨论分类

**⚠️ 这是讨论的关键步骤，不能跳过。**

### 数据来源优先级

1. **MEMORY.md** — 优先用，Agent 长期记忆
2. **memory/YYYY-MM-DD.md** — 每日日志
3. **skill 工作日志** — 某个 skill 的过程记录
4. **用户提供的文章/文档** — 需要整理的资料

### Prompt（照着念）

> "我想从我的记忆文件里，找出适合提取到 wiki 的内容。我们逐条讨论这些内容，看它们应该怎么归类到 wiki。"

---

### Step 1: 列出适合提取的内容

从 MEMORY.md 找出所有适合提取到 wiki 的内容。

**核心判断原则（必须记住）：**

| 类型 | 判断标准 | 为什么要记 |
|------|---------|-----------|
| **工具** | 第三方工具，拿来用就好 | **只记配置**（怎么用、参数是什么） |
| **项目** | 自己在开发/维护的系统 | **必须记规则**（设计决策、踩坑、标准） |

**关键区别：需不需要持续维护？**

- **工具**（如 Git、Docker、Obsidian）：是别人做好的，你拿来用。坏了找官方文档，不需要你维护它的规则。
- **项目**（如 Mauto、ChatERP）：是你在开发的，还没做完，规则和标准是为了你自己持续维护它。

**⚠️ 常见错误：**
> 把"项目的规则"当成"工具的使用方法"放到 `wiki/工具/`。
> 
> 错误原因：如果 Mauto 只是一个工具，你拿来用就好了，不需要记它的规则和标准。只有当它是一个项目时——这个项目还没有结束，你需要持续利用这些规则和标准来维护它——你才需要去记。

**正确做法：**
- Mauto 的规则 → `wiki/项目/`（因为 Mauto 是项目，需要持续维护）
- Git 的配置 → `wiki/工具/`（因为 Git 是工具，只记怎么用）

---

### Step 2: 逐条讨论

每条内容问两个问题：
1. 这是工具还是项目？
2. 如果是项目，它有没有**规则纪律/标准**需要记？

**判断标准（简单记住）：**
- **工具**：只记配置，不记规则
- **项目**：记规则和标准（因为要持续维护）

### Step 3: 提炼到 wiki

**判断规则：**

| 情况 | 处理方式 |
|------|---------|
| MEMORY.md 内容需要**重新整理**（从各section提取后重组） | 先写 raw/，再编译到 wiki/ |
| MEMORY.md 内容可以**直接复制**到对应 wiki .md | 直接写到 wiki/ |

**示例：**

从 MEMORY.md 提取项目内容（假设某项目 X）：
- 散落在多个 section（Projects、Key Decisions、Lessons Learned 等）
- 需要**重新整理**成项目结构（概述/**规则纪律**/踩坑等）
- → 先写 `raw/日记/X整理.md`，再编译到 `wiki/项目/X.md`

如果是一条已经整理好的规则，可以直接复制到 wiki 即可。

---

**根据 SCHEMA.md 提炼：**

从 raw/ 提炼到 wiki/ 时，必须根据 vault 的 SCHEMA.md 判断：
1. 内容放哪个 wiki/ 分类？
2. 页面格式按 SCHEMA.md 的模板
3. frontmatter 按 SCHEMA.md 的格式

---

**memory 和 wiki 的分工：**

| 位置 | 内容 |
|------|------|
| **MEMORY.md** | 项目检索指针（轻量） |
| **wiki/项目/** | 项目详细内容（丰富） |

**示例：**

MEMORY.md 里只需写：
```markdown
## 🏗️ Projects
- **Mauto** — 详见 wiki/项目/Mauto.md
- **obsidian-wiki-init** — 详见 wiki/项目/obsidian-wiki-init.md
```

不用在 MEMORY.md 里重复记规则，内容都在 wiki 里。

## Q3: wiki/ 需要哪些分类？（快速确认）

### 这是什么意思？

wiki/ 是**编译后的知识网络**，放整理好的结构化信息。

### 默认分类和含义

| 文件夹 | 存放什么 | 判断问题 |
|--------|---------|---------|
| **项目/** | 项目设计、决策 | 这是某个项目的设计吗？ |
| **工具/** | 工具配置、踩坑记录 | 这是工具的使用方法或限制吗？ |
| **实体信息/** | 人/客户具体信息 | 这是某个具体的人或客户吗？ |
| **知识概念/** | 概念、定义 | 这是抽象的道理或定义吗？ |
| **方法论/** | 方法、流程、最佳实践 | 这是\"怎么做\"的经验吗？ |
| **规则纪律/** | 规则、制度（禁止性） | 这是\"禁止做什么\"的清单吗？ |
| **参考与对比/** | A vs B、参考对比 | 这是两个东西的对比吗？ |
| **环境与社会关系/** | 环境认知、团队配置 | 这是团队/环境相关的吗？ |

### 讨论示例

> "wiki 默认分8类，每个文件夹有不同的判断标准。你有要调整的吗？比如 TS 可能需要加 `商品/` 或 `客户/` 分类？"

**讨论确认后，立即填到 SCHEMA.md：**
```markdown
## wiki/ 分类

| 文件夹 | 存放内容 |
|--------|---------|
| 项目/ | 项目设计、决策 |
| 工具/ | 工具配置、踩坑记录 |
| 实体信息/ | 人/客户具体信息 |
| 知识概念/ | 概念、定义 |
| 方法论/ | 方法、流程、最佳实践 |
| 规则纪律/ | 规则、标准 |
| 参考与对比/ | A vs B |
| 环境与社会关系/ | 环境认知、团队配置 |
```

## Q4: 命名规范用哪种？（快速确认）

### 这是什么意思？

wiki 里的文件怎么命名。

### 默认规则

- **不用前缀**，直接用内容名称
- 示例：`允林棠.md`、`API使用实践.md`、`ChatERP设计.md`

### 讨论示例

> "命名默认不用前缀，直接用内容名称。你有要改成前缀的吗？比如 `C-允林棠.md`、`P-商品名.md`？"

**讨论确认后，立即填到 SCHEMA.md：**
```markdown
## 命名规范

- 默认不用前缀，直接用内容名称
- 示例：`Mauto架构.md`、`飞书API调用规则.md`
```

## Q5: 编译触发条件？（快速确认）

### 这是什么意思？

什么时候把 raw 的材料编译到 wiki。

### 系统自动触发（默认规则，无需讨论）

| 条件 | 说明 |
|------|------|
| 同一文件夹 ≥3 条未编译 | raw/ 攒够了才提醒 |
| 单条 ≥7 天未编译 | 太久没动就提醒 |
| 预定讨论时间到了 | 约好了要讨论 |
| MEMORY.md > 350 行 | 记忆太满，建议迁移到 wiki |

### 讨论示例

> "编译触发默认系统自动检查，不需要你记。你有要额外加的规则吗？比如紧急材料要立即触发？"

**讨论确认后，立即填到 SCHEMA.md：**
```markdown
## 编译触发规则

系统自动触发，无需手动管理：
- 同一文件夹 ≥3 条未编译
- 单条 ≥7 天未编译
- 预定讨论时间到了
- MEMORY.md > 350 行
```

## 完整示例：从 raw 到 wiki 的一轮流程

### 场景

用户发来一篇关于"服装行业库存管理"的文章。

### Step 1: 写入 raw

```markdown
---
source: "https://example.com/article/123"
type: article
recorded: 2026-04-26
discussed_1st: 
compiled_1st: 
never_compiled: true
tags: [#库存管理, #服装]
---

[文章内容...]
```

### Step 2: Agent 判断分类

根据内容判断：
- 这是"库存管理的概念" → 放 `wiki/知识概念/`
- 这是"服装行业的实践" → 可以加 `实体信息/服装行业/`

### Step 3: 创建 wiki 页面

```markdown
---
type: concept
source: "https://example.com/article/123"
created: 2026-04-26
updated: 2026-04-26
tags: [#库存管理, #服装]
---

# 服装行业库存管理

## 定义

服装行业库存管理的核心挑战：...

## 关键要点

1. **季节性波动**：服装有淡旺季...
2. **SKU 多**：款号/颜色/尺码组合...
3. **追单周期**：...

## 相关概念

- [[库存周转率]]
- [[追单流程]]

## 来源

^[2026-04-26](https://example.com/article/123)
```

### Step 4: 更新 raw frontmatter

```yaml
compiled_1st: 2026-04-26
never_compiled: false
```

## _index.md 格式模板

每个 wiki/ 子目录应有 `_index.md`，汇总该目录下的页面。

```markdown
---
title: {目录名}
description: {一句话描述这个目录的内容}
---

# {目录名}

## 概述

{这个目录存放什么，为什么需要这个分类}

## 页面索引

| 页面 | 简介 | 状态 |
|------|------|------|
| [[页面名]] | 页面一句话描述 | ✅ 完整 / 🟡 待补充 |

## 最近更新

- 2026-04-26：[[页面名]] 创建

---

*由 OBHeartbeat 自动维护*
```

**示例：**

```markdown
---
title: 知识概念
description: 存放抽象概念、定义、行业术语
---

# 知识概念

## 概述

这个目录存放抽象的概念和定义，包括：
- 行业术语解释
- 方法论背后的原理
- 需要理解才能应用的知识

## 页面索引

| 页面 | 简介 | 状态 |
|------|------|------|
| [[库存周转率]] | 库存周转率计算公式和优化方法 | ✅ 完整 |
| [[追单流程]] | 服装追单的标准流程和周期 | ✅ 完整 |

## 最近更新

- 2026-04-26：[[库存周转率]] 创建

---

*由 OBHeartbeat 自动维护*
```

## 讨论中断时记录进度

如果讨论中途用户需要处理其他事：

### 记录模板

在 SCHEMA.md 开头记录当前进度：

```markdown
## 讨论进度

- [x] Q1: 完成 — "给 TS 用"
- [x] Q2: 完成 — "raw/ 采用默认 5 类"
- [ ] Q3: 进行中 — "wiki/ 分类，讨论到一半"
- [ ] Q4: 未开始
- [ ] Q5: 未开始

**下次继续**：从 Q3（wiki/ 分类）接着讨论
```

### 告诉用户

> "已记录讨论进度。下次继续时，我会从 Q3（wiki/ 分类）接着讨论。"

### 继续讨论时

1. 先读 vault SCHEMA.md 查看进度
2. 告诉用户：
> "上次讨论到 Q3（wiki/ 分类），还没确认。现在继续？"
3. 从中断处继续讨论

2. **填充 SCHEMA.md** — 根据讨论结果填入实际规则
3. **删除 `🟡 待填充` 标记** — 完成后标记为 `✅ 已确认`
